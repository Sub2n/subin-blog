# 긴 글 초안 만들기

## 구조 (태스크 회고)

작업 하나를 끝내고 정리하는 글은 `WRITING.md` 의 여섯 절을 따른다. **이전 상황 → 하려고 했던 것 → 내가 몰랐던 것 → 과정과 시행착오 → 결과 → 배운 것.**

- 「내가 몰랐던 것」이 이 블로그 글의 핵심이다. 개념을 처음 이해한 지점, 잘못 짐작하고 있던 것을 여기 모은다.
- 「과정과 시행착오」는 **핵심만.** 겪은 걸 전부 나열하면 목록이 되지 글이 되지 않는다. 방향을 바꾼 결정, 원인을 잘못 짚었던 것, 크게 터진 사고 4~6개까지. 사소한 삽질은 버린다.
- 「배운 것」은 3~4개. 작업 요약을 반복하지 말고 다음에 판단이 달라질 것만 쓴다.

## 절차
1. 주제를 듣고 **개요를 먼저 제안**한다: 제목 후보 2개, 위 여섯 절에 각각 한 줄 요지. 사용자가 고르면 다음으로.
2. 관련 기존 글을 찾는다: `grep -ril "<키워드>" src/content/posts | head`. 있으면 본문 끝 `## 관련 글` 에 상대 경로가 아닌 사이트 주소(`/posts/...` 또는 `/2019/...`)로 링크한다. 예전 글의 주소는 frontmatter `path` 값이다.
3. `src/content/posts/<YYYY>/<slug>.md` 에 저장한다. `draft: true` 로 시작한다.
4. 본문 규칙:
   - 첫 문단은 독자가 이 글을 읽어야 하는 이유 (문제·맥락) 3문장 이내.
   - 소제목은 `##` 만 쓰고, 소제목 하나에 한 가지 주장.
   - 코드 블록은 언어를 명시하고 15줄을 넘기면 나눈다.
   - 마무리 소제목("정리", "앞으로", "느낀 점")을 붙이지 않는다. 내용이 끝나면 글도 끝난다. 감상을 문단으로 만들지 않는다. 대신 사실 바로 옆에 한 문장으로 붙인다.
5. `description` 을 120자 이내로 채운다 (검색 결과와 공유 카드에 쓰인다).
6. `npm run build` 통과를 확인하고, 파일 경로와 주소를 알려준다. 발행하려면 `draft: false` 로 바꾸라고 안내한다.

## 말투 (쓰기 전에 반드시)

**본문을 쓰기 전에 `WRITING.md` 의 「말투」 절을 읽는다.** 2019년 글 168편을 세어서 뽑은 규칙이라 추측으로 대체하지 않는다. 긴 글에서 특히 틀리기 쉬운 것들:

- **보고서가 되지 않게.** "원인: …", "결과: …" 식으로 끊어 쓰면 이 블로그 글이 아니다. 같은 사실을 사람이 말하듯 문장으로 쓴다.
- **접속사로 문단을 시작하지 않는다.** 168편에 "그래서"·"하지만"으로 시작한 문장이 0회다. 연결은 문장 안에서 "즉"(94회), "따라서"(49회), "또"(69회), "대신"(20회)으로.
- **반응은 사실 바로 옆에 한 문장.** "이 숫자를 보고 좀 놀랐다", "여기서 하루를 날렸다", "이건 좀 아찔했다". 문단을 따로 만들면 군더더기가 된다.
- **막혔던 것과 틀렸던 것을 그대로 쓴다.** 결정이 뒤집힌 과정, 원인을 잘못 짚었던 것까지.
- 1인칭은 아껴 쓴다. 볼드는 문장을 통째로. 느낌표는 문단당 하나까지.

긴 글의 기준 사례는 `src/content/posts/2019/Fastflix.md`(회고)와 `src/content/posts/2026/` 의 인프라 글 세 편이다.

## 지키기
- 사용자의 경험이 아닌 일반론으로 채우지 않는다. 빈 곳은 `<!-- TODO -->` 로 남기고 질문한다.
- 회사 정보가 들어가는 글이면 시크릿, 계정, 내부 호스트명, 고객 앱 이름을 빼고 쓴 뒤 무엇을 남겼는지 보고한다.
