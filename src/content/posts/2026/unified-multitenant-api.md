앱이 45개고 100개까지 늘릴 계획이다. 그런데 사용자는 상위 3개에 몰려 있다. 나머지 앱은 사용자가 거의 없는데도 API 컨테이너랑 워커 컨테이너를 하나씩 차지하고 있다. 시간이랑 생산성이 아까워서 통합하기로 했다. 9월 17일부터 18일까지 이틀 동안 dev까지 전환했고 prod는 아직이다.

## 이전 환경

- nx 모노레포. 같은 Docker 이미지를 `TARGET_PROJECT` env만 바꿔서 앱마다 API 컨테이너 + 워커 컨테이너로 띄운다. prod는 API 49개 + 워커 48개, 합쳐서 컨테이너 97개.
- 컨테이너당 메모리 상한 2GB. 사용자가 0명인 앱도 4GB를 예약하고 있다.
- 그런데 실제로 재 봤더니 RSS는 앱별 API 230~280MB, 워커 230~590MB였다. 상한이 문제가 아니라 **앱 수 × 고정비 230MB**가 곱해지는 구조가 문제였다. 이걸 재 보기 전까지는 "2GB씩 낭비"라고 생각하고 있었는데 숫자를 보니 얘기가 좀 달랐다.
- 앱 하나 추가할 때 손으로 하는 일이 꽤 된다. LB 규칙, 포트 배정, 서버 배치, `.env`, Firebase 키, module-selector case, 앱 모듈 4개, 배포 스크립트.
- 사용자 없는 앱의 워커도 큐를 계속 찔러 대서 Redis가 힘들어하고 있었다. 재 보니 prod Redis가 초당 53,000 명령, 연결 7,485개(그중 1,840개가 BullMQ 소비자의 blocking), 1.6코어 상시 점유. 이 숫자를 보고 이건 진짜 손봐야겠다 싶었다.
- 롤링 배포, 헬스 대기, 불변 이미지 태그가 전부 없었다. `:latest`만 push하니 롤백도 안 된다.

다행히 이미 되어 있던 것도 있었다. MongoDB는 단일 인스턴스에 앱별 database, Redis는 전 앱 공용에 키 prefix로 구분, 전 앱의 Mongo URI랑 Firebase 서비스 계정이 이미지 하나에 다 들어 있었다. 통합의 절반은 이미 돼 있었던 셈이다.

## 처음 생각한 것

- API 헤더의 bundle ID로 프로젝트를 구분한다.
- API, 워커, DB를 전부 통합한다. Firebase 인증도 통합하고 사용자 DB도 합칠 수 있는지 본다.
- 기존 앱별 API는 유지한 채 사용자 적은 앱부터 파일럿.
- 배포 워크플로에 TARGET_PROJECT 넣듯이 통합 플래그를 추가한다.

조사해 보니 전제가 몇 개 틀려 있었다.

- 배포 워크플로에는 TARGET_PROJECT 입력이 아예 없었다. 페이즈당 이미지 하나를 공유하고 앱 구분은 compose env가 한다. 통합 플래그는 워크플로가 아니라 compose 생성기랑 루트 모듈에 들어가야 했다.
- 자체 JWT가 없었다. Firebase ID 토큰 단일 경로고 프로젝트가 앱마다 다르다. 그래서 "헤더로 Firebase 앱을 고르고, 그 앱으로 verifyIdToken이 성공해야 테넌트 확정. aud 불일치면 401"로 갔다.
- 이미 배포된 앱은 API URL을 못 바꾸고 bundle ID 헤더도 안 보낸다. 기존 호스트는 영구히 살려 둬야 한다.

## 기각한 것

**DB 통합.** User 스키마에 테넌트 필드가 없고 유니크 인덱스가 DB 경계에 기대고 있다. 모델 116개에 테넌트 필드를 넣고 백필해야 한다. 여기까지 보고 접었다. 앱별 database는 그대로 두고 프로세스랑 커넥션 풀만 합치기로.

**Firebase 사용자 풀 통합.** uid가 프로젝트 단위라서 합치면 45개 앱의 FCM 토큰이 전부 무효가 되고 스토어 재배포까지 필요하다. 이건 아예 선택지가 아니었다. 앱당 프로젝트 1개를 유지하고, 한 프로세스가 N개 프로젝트 토큰을 검증하는 쪽으로.

**어드민 토글로 통합 여부 제어.** 처음엔 앱 관리 화면에서 켜고 끄고 싶었는데, 스위치가 라우팅이랑 워커 둘이고 dev/qa nginx는 어드민이 못 건드린다. 배포할 때 meta의 `apiUrl` 값을 바꾸고 gen-apps 하는 방식으로 정리했다.

**nginx에서 테넌트 헤더 주입.** dev용으로 한 번 만들었다가 apiUrl 방식으로 가면서 걷어냈다. 어느 페이즈도 헤더를 신뢰하지 않는다.

## 테넌트가 뭔지부터 물어봤다

프론트엔드만 하다 보니 "테넌트"라는 말부터 낯설었다. 이게 뭔지, 지금 Firebase 인증이 어떻게 돌아가고 백엔드 인프라가 어떤 구조인지부터 쉽게 설명해 달라고 했다.

테넌트는 세입자다. 건물(프로세스) 하나에 세입자(앱) 여럿이 사는데, 각자 자기 방(DB, 캐시 namespace, 큐 prefix)만 쓴다. 요청이 들어오면 route param으로 누구 방인지 정하고, route guard가 남의 방에 못 들어가게 막는다.

이 비유를 듣고 나서야 설계가 읽혔다. 결국 내가 프론트에서 매일 하던 라우팅이랑 가드였다.

## 어떻게 만들었나

- 같은 `apps/api`에 `TARGET_PROJECT=unified-api` 모드를 추가했다. 앱별 모드에서는 모든 tenant-aware 래퍼가 원본을 그대로 돌려준다. 코드는 하나고 동작만 둘이다.
- 테넌트 컨텍스트는 `AsyncLocalStorage`. DI 토큰 뒤에 ES Proxy를 두고 컨텍스트로 해석한다.
- Mongo는 `useDb`로 풀 하나를 공유하고, **기본 연결에는 모델을 0개** 둔다. populate가 부모 연결로 조용히 폴백하는 게 제일 무서운 시나리오라, 아예 MissingSchemaError가 나게 막았다. 조용히 다른 앱 데이터를 읽는 것보다 터지는 게 낫다.
- 캐시 namespace, 큐 prefix, scheduler id는 앱별 API랑 바이트 단위로 같게 하고 spec으로 고정했다. 그래야 두 스택이 같은 DB·캐시·큐를 보면서 공존할 수 있다.
- 소켓은 통합 adapter를 만들려다 접었다. 대신 앱별 채널을 구독해서 방 이름만 바꿔 로컬로 전달하는 브리지로 갔다. 이러면 구버전 빌드랑 같은 채팅방에서 만난다.
- 앱 전용 기능은 `@TenantOnly` + 전역 가드(404) + 서비스 진입부 `assertTenant` + DB 분리로 겹겹이 막았다. 다른 앱 토큰은 401, 다른 앱의 전용 엔드포인트는 404인 걸 로컬에서 확인했다.
- 선행으로 고친 것도 있다. Dockerfile에 `.env.qa` 누락, graceful drain + `/health/lb`, `:sha-` 불변 이미지 태그, 포트가 겹치면 gen-apps가 실패하게.

테넌트 식별은 헤더가 아니라 **URL 경로의 `<apiName>`**으로 정했다. dev가 이미 `/kpop-api` 경로 방식이었고, 클라이언트 코드를 안 바꿔도 되고, AdMob 콜백이나 웹훅처럼 헤더를 못 붙이는 외부 호출도 갈린다. 되돌릴 때는 apiUrl을 되돌려서 배포하면 된다. 네이티브는 스토어 배포를 거쳐야 해서 롤백이 느린데, 그게 이 방식의 대가다.

걱정했던 것 하나는 실측으로 지웠다. Fastify body 파싱 뒤에 AsyncLocalStorage가 유실되는지 봤는데 Node 24 + Fastify 5에서는 keep-alive 연속 요청에서도 멀쩡히 유지됐다.

## 파일럿

dev 파일럿은 kpop으로 잡았다. 앱 전용 기능이 가장 많아서 2중 방어랑 전용 리스너, 큐 필터가 실제로 검증되고, qa 페이즈를 지원하는 유일한 앱이라서. kpop의 prod는 상위 앱이라 dev만 건드렸다.

- nginx에 `location /unified-api/` 하나만 추가했다. 앱 옮길 때마다 고칠 필요가 없게.
- 앱별 kpop API는 `legacyApi: keep`으로 살려 뒀다. 구버전 빌드가 예전 주소를 계속 부르니까. 앱별 워커만 내렸다.
- 클라이언트 배포하고 나니 로그에 unified-api로 찍히고, 에러 0, 브리지도 정상.

중간에 "기존 API에는 진짜 아무 변화도 없는 거지?"를 물었는데 답은 "아니다"였다. 같은 이미지를 쓰니까 코드는 바뀌었고 동작만 같은 거다. 이건 좀 뜨끔했다. 공용 코드를 먼저 배포하고 나중에 플래그를 켜는 단계를 권유받았는데 그건 생략했다.

## Redis 과부하는 이걸로 안 풀렸다

통합 API로 옮겼는데 워커의 큐 소비자는 그대로였다. 통합 워커 하나가 앱별 prefix 40개를 각각 구독하니까 앱 수 × 큐 수만큼 소비자가 생긴다. 앱을 더 얹을수록 늘어나는 구조는 바뀐 게 없었다.

그래서 **큐 prefix를 하나로 합치고 잡에 앱 정보를 싣는** 방식을 제안했다.

- `queueMode: legacy | shared`. shared 앱은 `<env>-unified` prefix 하나만 쓴다.
- 잡 데이터에 `__pixelsTenant`를 싣고, jobId·dedup·scheduler id에 `<appKey>~` 접두를 붙인다.
- `getJobSchedulers`는 자기 앱 것만 보게 했다. 안 가리면 부팅할 때 남의 반복 잡을 지워 버린다.
- `setGlobalConcurrency(1)`은 무시한다. 앱 간 직렬화를 막으려고.
- 프로세서당 소비자는 1개. 앱 수랑 무관해졌다.

실측해 보니 kpop 하나일 때 통합 워커의 Redis 소켓이 84개(앱별 40 + 공용 40 + 4)였다. 앱을 더 얹어도 공용 40은 그대로다. 이 구조가 맞다는 확신이 여기서 생겼다.

그리고 원인 하나를 따로 찾았다. prod 새 잡이 초당 725건인데 그중 98%가 통합검색 projection이었다. reconciliation이 5분마다 projection 없는 원본을 전부 다시 넣는데, 색인할 게 없어서 지운 원본은 표시가 안 남아 영원히 반복되고 있었다. 사용자가 한 명도 없는 앱에서도 분당 1,800건이 돌고 있었다. 완료 패스 시작 시각을 남기고 그 뒤에 바뀐 원본만 넣게 고쳤다. 통합이랑 무관한 버그라 커밋은 따로 분리했다.

## dev 36개 앱 전환

부하 시험(동시성 20, 30초)에서 통합이랑 앱별이 289 vs 282 rps, 인증+DB 경로가 348 vs 344였다. 테넌트 분기 비용이 오차 안이었다. 생각보다 공짜라서 dev는 거의 다 옮겨도 되겠다 싶었다. 통합 범위 36개 앱을 한 번에 전환했다.

- 확인해 보니 dev에 실제로 떠 있던 앱별 API는 4개뿐이었다. 나머지 32개는 dev API가 아예 없던 앱이라 통합으로 처음 서비스되는 셈이었다.
- 설치된 dev 빌드가 예전 주소를 부르니까, 앱별 API가 내려간 앱의 `/<apiName>/`을 통합 API로 넘기는 nginx fallback을 생성기에 넣었다. 덕분에 클라이언트 재배포 없이 그냥 동작한다.
- 결과가 꽤 극적이었다. 워커 Redis 소켓이 44개. 앱별 prefix 방식이었으면 1,440개다. 워커 RSS 513~522MB로 앱당 약 2.5MB, API 301~340MB로 앱당 약 0.6MB. dev Redis 클라이언트는 908 → 678, ops/s는 15k → 5.9k.

"dev 어떤 앱에서 unified-api를 호출 안 하는 것 같은데?"라고 물어봤다가, URL에 안 보일 뿐 통합이 처리하고 있다는 걸 알았다. 그래서 예전 주소로 불러도 밖에서 확인할 수 있게 `X-Pixels-Served-By: unified-api/<appKey>` 헤더를 붙였다. 내가 눈으로 확인 못 하면 답답해서 못 넘어간다.

## 터진 것들

**로컬 워커가 dev 잡을 먹었다.** 로컬에서 통합 워커를 띄웠더니 로컬 prefix에 남아 있던 대기 잡 하나가 처리돼서 dev 테스트 사용자한테 푸시가 나갔다. 알림 받고 나서야 알았다. 이후로 워커는 로컬에서 안 띄우고 spec으로만 검증한다.

**앱 키 마커가 검증에 걸렸다.** 잡 데이터에 실은 `__pixelsTenant`가 프로세서까지 그대로 넘어가서, 키 개수를 세는 통합검색 projection 검증에 걸려 501건이 즉시 실패했다. 워커가 테넌트를 확정한 뒤에 마커를 떼고 넘기게 고쳤다.

**그걸 고치니까 기존 버그가 드러났다.** 9월 1일 커밋부터 reconciliation이 키 3개를 넣는데 프로세서는 2개만 받고 있어서, reconciliation 잡이 전부 실패하고 있었다. 앱별 prefix 쪽에도 failed가 1,000건(보존 상한)이었다. 아침에 본 725 jobs/s의 실체가 이 실패랑 재시도였을 가능성이 크다. 처음엔 내가 만든 churn 수정 때문인 줄 알았는데 아니었다.

**부팅이 8~9분 걸렸다.** 36 테넌트 준비는 앱당 0.2~0.3초라 문제가 아니었다. 나머지가 전부 shared 앱의 앱별 prefix 정리 중에 큐마다 키 공간을 SCAN하는 중복 방지 키 청소였다. 앱당 16초 × 36개. scheduler 삭제만 하게 줄이니 21초가 됐다.

**큐 facade에서 `this`가 사라졌다.** `remove`랑 `getJobSchedulers`를 큐 객체에서 떼어내서 호출하는 바람에 BullMQ 내부 `this`가 없어졌다. `Cannot read properties of undefined (reading 'trace')`. 에러 메시지만 봐서는 원인을 짐작하기 어려운 종류였다. `this`에 의존하는 가짜 큐를 만들어 회귀 spec을 붙였다.

**MaxListenersExceededWarning.** 워커 40개가 Redis 연결 하나에 리스너를 달아서 기본 상한 10을 넘었다. 누수는 아니라 상한만 풀었다.

**모니터가 30분 동안 조용했다.** 이상이 없어서 조용한 줄 알았는데, 파이프 마지막 `cut`의 출력 버퍼링 때문에 감시 출력 자체가 안 나오고 있었다. 조용한 감시가 제일 위험하다.

중간에 "그니까 CPU 터지면 어떡해"도 물어봤다. Node는 단일 스레드라 통합 API 컨테이너 하나가 사실상 코어 하나다. 대응은 복제본을 늘리고, 무거운 앱은 별도 샤드나 앱별 API로 되돌리는 것. 상위 앱은 처음부터 별도 샤드로 둔다.

## 지금 구조

dev 기준으로 요청이 이렇게 흐른다.

클라이언트 → nginx(`/unified-api/`는 통합 API로, 내려간 앱은 `/<apiName>/`도 fallback) → 통합 API가 라우터 앞 raw HTTP 서버에서 경로 첫 조각 `<apiName>`을 떼어 레지스트리 조회 → AsyncLocalStorage에 테넌트 저장 → 컨트롤러, DB, 캐시, 큐, Firebase named app이 전부 컨텍스트로 해석.

모르는 앱은 404, 신호가 충돌하면 400, 컨텍스트 없이 접근하면 throw. 전부 fail-closed다.

- 큐는 shared 앱이 공용 prefix를 쓰고, legacy 앱은 앱별 prefix로 격리할 수 있다. 상위 앱용으로 남겨 뒀다.
- dev는 통합 범위 36개 앱 전부 통합 API·워커로 돌고 있다. 전용 모듈이 있는 앱 9개랑 admin 계열은 범위 밖이다.
- prod는 아무것도 안 떴다. prod에서 켜려고 하면 gen-apps가 막는다.

## 남은 것

- prod 파일럿 준비. 통합 호스트 2대 결정, LB/DNS 규칙, 롤링 배포 스크립트, 워크플로 `target` 입력, 어드민 배포 화면.
- 테넌트 프로비저닝 CLI, 테넌트별 동시성 상한, Sentry·로그 테넌트 태그.
- 범위 밖 앱 6개 편입.
- dev 하루 안정화 관찰. 신규 32개 앱의 통합검색 첫 패스 때문에 워커 CPU가 78~123%까지 올라갔다.

prod는 dev에서 실측까지 다 끝내고 안정적으로 검증된 다음에만 넘어갈 생각이다.
