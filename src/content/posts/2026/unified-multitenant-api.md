앱이 45개고 100개까지 늘릴 계획이다. 그런데 사용자는 상위 3개에 몰려 있다. 9월 17일부터 18일까지 이틀 동안 dev까지 전환했고 prod는 아직이다.

## 이전 상황

- 같은 Docker 이미지를 env만 바꿔서 앱마다 API 컨테이너 + 워커 컨테이너로 띄운다. prod는 합쳐서 컨테이너 97개.
- 컨테이너당 메모리 상한 2GB. 사용자가 0명인 앱도 4GB를 예약하고 있다.
- 앱 하나 추가할 때 손으로 하는 일이 꽤 된다. LB 규칙, 포트 배정, 서버 배치, env, 앱 모듈 4개, 배포 스크립트.
- 사용자 없는 앱의 워커도 큐를 계속 찔러 대서 Redis가 힘들어했다. 재 보니 초당 53,000 명령, 연결 7,485개, 1.6코어 상시 점유였다.
- 롤링 배포도 불변 이미지 태그도 없었다. `:latest`만 push하니 롤백이 안 된다.

## 하려고 했던 것

시간이랑 생산성이 아까워서 통합하기로 했다.

- API, 워커, DB를 전부 통합한다. 인증이랑 사용자 DB도 합칠 수 있는지 본다.
- 기존 앱별 API는 유지한 채 사용자 적은 앱부터 파일럿으로.
- 배포할 때 통합 여부를 플래그로 켠다.

## 내가 몰랐던 것

**테넌트가 뭔지 몰랐다.** 이게 뭔지, 인증이 어떻게 돌아가고 백엔드 구조가 어떤지부터 쉽게 설명해 달라고 했다. 테넌트는 세입자다. 건물(프로세스) 하나에 세입자(앱) 여럿이 사는데 각자 자기 방(DB, 캐시, 큐)만 쓴다. 요청이 들어오면 route param으로 누구 방인지 정하고 route guard가 남의 방에 못 들어가게 막는다. 이 비유를 듣고 나서야 설계가 읽혔다. 결국 내가 프론트에서 매일 하던 라우팅이랑 가드였다.

**문제를 잘못 짚고 있었다.** 컨테이너마다 2GB씩 잡아먹는 게 문제인 줄 알았다. 실제로 재 보니 RSS는 API가 230~280MB, 워커가 230~590MB였다. 상한이 아니라 **앱 수 × 고정비 230MB가 곱해지는 구조**가 문제였다.

**Node가 단일 스레드라는 게 여기서 의미가 달라진다.** "CPU 터지면 어떡해"를 물어봤는데, 통합 API 컨테이너 하나가 사실상 코어 하나다. 앱별로 흩어져 있을 때는 자연스럽게 분산돼 있던 게, 합치면 한 프로세스에 몰린다. 대응은 복제본을 늘리고 무거운 앱은 별도 샤드로 빼는 것이다.

## 과정과 시행착오

**조사해 보니 초기 전제가 몇 개 틀려 있었다.** 배포 워크플로에는 플래그를 넣을 자리가 아예 없었다. 페이즈당 이미지 하나를 공유하고 앱 구분은 compose env가 한다. 자체 JWT도 없어서 인증 경로가 생각과 달랐다. 그리고 이미 배포된 앱은 API 주소를 못 바꾼다. 기존 호스트를 영구히 살려 두는 게 전제가 됐다.

**DB 통합이랑 사용자 풀 통합은 기각했다.** DB는 모델 116개에 테넌트 필드를 넣고 백필해야 해서 접었다. 사용자 풀은 합치면 45개 앱의 푸시 토큰이 전부 무효가 되고 스토어 재배포까지 필요해서 아예 선택지가 아니었다. 앱별 DB는 그대로 두고 프로세스랑 커넥션 풀만 합치기로 했다.

**테넌트 식별은 헤더가 아니라 URL 경로로 갔다.** 클라이언트 코드를 안 바꿔도 되고, 외부 웹훅처럼 헤더를 못 붙이는 호출도 갈린다. 되돌릴 때는 주소를 되돌려서 배포하면 된다.

가장 조심한 건 **조용히 새는 경로**였다. Mongo는 풀 하나를 공유하되 기본 연결에는 모델을 0개 둬서, 컨텍스트 없이 접근하면 에러가 나게 했다. 다른 앱 데이터를 조용히 읽는 것보다 터지는 게 낫다.

**통합만으로는 Redis가 안 풀렸다.** 통합 워커 하나가 앱별 prefix 40개를 각각 구독하니 소비자 수는 그대로였다. 그래서 큐 prefix를 하나로 합치고 잡에 앱 정보를 싣는 방식으로 바꿨다. 프로세서당 소비자 1개, 앱 수와 무관해졌다.

**그 과정에서 기존 버그가 드러났다.** 잡에 실은 앱 키 마커가 프로세서까지 넘어가서 payload 검증에 걸려 501건이 즉시 실패했다. 마커를 떼고 넘기게 고쳤더니, 이번엔 9월 1일부터 같은 검증이 계속 실패하고 있었다는 게 보였다. 아침에 본 초당 725건의 잡 폭주가 사실 이 실패랑 재시도였을 가능성이 크다.

**부팅이 8~9분 걸렸다.** 36개 테넌트 준비는 앱당 0.2~0.3초라 문제가 아니었다. 범인은 큐마다 키 공간을 SCAN하는 중복 방지 키 청소였다. 앱당 16초 × 36개. 정리 범위를 줄이니 21초가 됐다.

**감시가 30분 동안 조용했다.** 이상이 없어서 조용한 줄 알았는데, 파이프 마지막 명령의 출력 버퍼링 때문에 감시 출력 자체가 안 나오고 있었다.

## 결과

부하 시험에서 통합이랑 앱별이 289 vs 282 rps, 인증+DB 경로가 348 vs 344였다. 테넌트 분기 비용이 오차 안이라 dev는 거의 다 옮겨도 되겠다 싶었다. 통합 범위 36개 앱을 한 번에 전환했다.

- 워커의 Redis 소켓이 44개. 앱별 prefix 방식이었으면 1,440개다.
- 워커 RSS 513~522MB로 앱당 약 2.5MB, API는 앱당 약 0.6MB.
- dev Redis 클라이언트 908 → 678, 초당 명령 15k → 5.9k.
- 설치된 dev 빌드는 재배포 없이 그대로 돈다. 앱별 API가 내려간 앱은 nginx가 통합 API로 넘긴다.

prod는 아직 아무것도 안 떴다. prod에서 켜려고 하면 생성기가 막는다. dev에서 실측까지 다 끝내고 검증된 다음에만 넘어갈 생각이다.

## 배운 것

- **재기 전에는 문제를 잘못 짚는다.** 2GB 상한이 문제라고 믿고 시작했는데 실제 범인은 고정비였다. 만약 상한만 줄였으면 아무것도 나아지지 않았을 거다.
- **한 층을 고치면 다음 층이 드러난다.** 프로세스를 합쳐도 큐 소비자는 그대로였고, 큐를 합치고 나서야 보름 전부터 실패하던 잡이 보였다. 병목은 한 번에 하나씩만 보인다.
- **조용한 감시가 제일 위험하다.** 30분 동안 아무 일 없는 줄 알았는데 감시가 말을 못 하고 있었다. 감시를 붙였으면 감시가 살아 있는지도 봐야 한다.
- **합치면 격리가 사라진다.** 앱별로 떠 있을 때는 한 앱이 죽어도 나머지가 멀쩡했다. 이걸 대신할 장치를 설계 안에 넣어야 한다. 전용 기능마다 가드를 겹겹이 두고, 컨텍스트가 없으면 조용히 넘어가지 말고 터지게 만든 이유다.
