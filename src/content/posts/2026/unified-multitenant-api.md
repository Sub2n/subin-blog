앱이 45개고 100개까지 늘릴 계획이다. 그런데 사용자는 상위 3개에 몰려 있다. 9월 17일에 시작해서 23일까지 운영 30개 앱을 통합 API로 옮겼다. 앱별 컨테이너 없이 서비스되고 있고 다운타임은 없었다.

## 이전 상황

- 같은 Docker 이미지를 env만 바꿔서 앱마다 API 컨테이너 + 워커 컨테이너로 띄운다. 운영은 합쳐서 컨테이너 97개.
- 컨테이너당 메모리 상한 2GB. 사용자가 0명인 앱도 4GB를 예약하고 있다.
- 앱 하나 추가할 때 손으로 하는 일이 꽤 된다. LB 규칙, 포트 배정, 서버 배치, env, 앱 모듈 4개, 배포 스크립트.
- 사용자 없는 앱의 워커도 큐를 계속 찔러 대서 Redis가 힘들어했다. 재 보니 초당 78,815 명령, 연결 7,475개였다.
- 롤링 배포도 불변 이미지 태그도 없었다. `:latest`만 push하니 롤백이 안 된다.

## 하려고 했던 것

시간이랑 생산성이 아까워서 통합하기로 했다.

- API, 워커, DB를 전부 통합한다. 인증이랑 사용자 DB도 합칠 수 있는지 본다.
- 기존 앱별 API는 유지한 채 사용자 적은 앱부터 파일럿으로.
- 모든 설계와 검증을 dev에서 끝내고, 실측까지 마친 것만 운영에 올린다.

## 내가 몰랐던 것

**테넌트가 뭔지 몰랐다.** 이게 뭔지, 인증이 어떻게 돌아가고 백엔드 구조가 어떤지부터 쉽게 설명해 달라고 했다. 테넌트는 세입자다. 건물(프로세스) 하나에 세입자(앱) 여럿이 사는데 각자 자기 방(DB, 캐시, 큐)만 쓴다. 요청이 들어오면 route param으로 누구 방인지 정하고 route guard가 남의 방에 못 들어가게 막는다. 이 비유를 듣고 나서야 설계가 읽혔다. 결국 내가 프론트에서 매일 하던 라우팅이랑 가드였다.

**문제를 잘못 짚고 있었다.** 컨테이너마다 2GB씩 잡아먹는 게 문제인 줄 알았다. 실제로 재 보니 RSS는 API가 230~280MB, 워커가 230~590MB였다. 상한이 아니라 **앱 수 × 고정비 230MB가 곱해지는 구조**가 문제였다.

**메모리 상한은 예약이 아니라 천장이다.** 전환 대상 앱들의 상한을 낮추면 메모리가 회수될 줄 알았다. 한 호스트의 상한 합계가 40,458MB로 물리 메모리 7,941MB의 5배인데도 실사용은 4,325MB였다. 상한을 낮춰도 그 앱이 덜 쓰지 않는다. **회수하려면 컨테이너를 내리는 수밖에 없다.**

**Node가 단일 스레드라는 게 여기서 의미가 달라진다.** "CPU 터지면 어떡해"를 물어봤는데, 통합 API 컨테이너 하나가 사실상 코어 하나다. 앱별로 흩어져 있을 때는 자연스럽게 분산돼 있던 게 합치면 한 프로세스에 몰린다. 대응은 복제본을 늘리고 무거운 앱은 별도 샤드로 빼는 것이다.

## 과정과 시행착오

**조사해 보니 초기 전제가 몇 개 틀려 있었다.** 배포 워크플로에는 플래그를 넣을 자리가 아예 없었다. 자체 JWT도 없어서 인증 경로가 생각과 달랐고, 이미 배포된 앱은 API 주소를 못 바꾼다. 기존 호스트를 영구히 살려 두는 게 전제가 됐다.

**DB 통합이랑 사용자 풀 통합은 기각했다.** DB는 모델 116개에 테넌트 필드를 넣고 백필해야 해서 접었다. 사용자 풀은 합치면 45개 앱의 푸시 토큰이 전부 무효가 되고 스토어 재배포까지 필요해서 아예 선택지가 아니었다. 앱별 DB는 그대로 두고 프로세스랑 커넥션 풀만 합치기로 했다.

**통합만으로는 Redis가 안 풀렸다.** 통합 워커 하나가 앱별 prefix 40개를 각각 구독하니 소비자 수는 그대로였다. 그래서 큐 prefix를 하나로 합치고 잡에 앱 정보를 싣는 방식으로 바꿨다. 프로세서당 소비자 1개, 앱 수와 무관해졌다.

**전 테넌트를 한 번에 죽이는 함정이 세 종류 있었다.** 혼자 뜨던 프로세스를 합치면 사고의 반경이 달라진다는 걸 여기서 배웠다.

- **부팅 훅.** `onModuleInit`에서 테넌트 DB를 읽는 코드가 있었다. 통합 프로세스는 부팅 시점에 테넌트가 없어서 프록시가 던지고, 컨테이너가 재시작 루프에 빠졌다. 타입체크·빌드·유닛 테스트가 전부 통과한 뒤 실제 부팅에서만 드러났다. 소스 스캔 가드로 못 박았다.
- **라우트 충돌.** 한 Fastify 인스턴스에 컨트롤러가 몰리니 같은 메서드·경로가 겹치면 부팅이 거부된다. 전용 컨트롤러 15개에 테넌트 표시를 붙이고, Nest 메타데이터로 충돌을 잡는 spec을 뒀다.
- **기본 연결.** 원본 `@InjectConnection`이 앱별 DB가 아니라 기본 연결에 묶였다. 모델은 테넌트 연결인데 트랜잭션 세션은 기본 연결이라 쓰기가 연결을 넘나들었다. 앱별 API에서는 래퍼가 그대로 통과하니까 증상이 안 나온다.

**리스너 하나가 41개 앱의 이벤트를 받는다.** 자동입장 리스너에 필터가 없으면 A앱 사용자가 B앱 방에 들어간다. 이런 건 합치기 전에는 존재할 수 없던 버그다.

**브랜치를 잘못 알고 있었다.** qa에만 올린 커밋이 dev에 반영되지 않아서 통합 테넌트가 404로 떴다. dev 이미지는 main에서 빌드된다. main은 개발, qa는 테스트, release는 운영 배포인데 이걸 혼동해서 하루를 날렸다. 스킬 문서에 못 박아 뒀다.

**응답이 느려졌는데 통합 탓이 아니었다.** 운영이랑 dev가 같이 느려져서 통합을 의심했다. 재 보니 Redis가 `SCAN`으로 포화돼 있었다. 초당 8,129회, **Redis CPU의 85.7%**. Redis는 단일 스레드라 SCAN이 CPU를 85% 먹으면 캐시 조회도 큐도 세션도 전부 그 뒤에 줄을 선다. 통합이 느린 게 아니라 그 Redis를 쓰는 모두가 같이 느렸던 거다.

원인은 통화 상태 조회였다. 통화 요청마다 발신·수신 2회씩 전 키스페이스를 훑는데, 대부분 "통화 중 아님"이라는 빈 결과를 얻으려고 그랬다. 초당 약 1건의 조회가 Redis CPU 85%를 먹고 있었다. 트래픽 문제가 아니라 조회 비용 문제였다. Lua로 활성 통화 인덱스를 유지하고 읽기를 인덱스로 돌렸다.

## 결과

운영 30개 앱이 앱별 컨테이너 없이 통합 API로만 서비스된다. 12개 → 8개 → 6개 → 4개, 네 번에 나눠서 옮겼다.

**배포 순서가 네 단계로 굳었다.** 이게 이번 과제에서 제일 중요한 산출물이다.

1. **워커 전환** — 앱별 워커만 내려가고 API는 남는다. 사용자 영향 0.
2. **LB flip** — 옛 호스트를 통합 타깃 그룹으로. HTTP는 즉시 넘어간다.
3. **소켓 잔향 0 확인** — 옛 컨테이너에 신규 소켓이 안 붙는지 본다. flip 직후 1~3분은 남는다.
4. **앱별 API 정지** — 컨테이너를 내리고 메모리를 회수한다.

3번을 건너뛰면 사용자가 끊긴다. 사용자 4,124명짜리 앱에서 flip 직후 3분간 신규 소켓 23건이 붙었고, 60초 표본이 8건에서 0건으로 떨어지는 걸 보고 내렸다. **소켓 잔향은 앱이 클수록 크다.**

**메모리는 세 호스트에서 약 8.4GB를 회수했다.**

| 항목 | 전환 전 | 지금 |
|---|---|---|
| 호스트 3대 가용 메모리 합 | 8.5 GB | 16.9 GB |
| 컨테이너 수 | 40 | 10 |
| 통합 API | — | 415~507 MB (30개 앱) |
| 통합 워커 | — | 722 MB |

앱이 12개일 때 API가 290MB, 20개일 때 343MB, 30개일 때 415MB였다. **앱당 6MB꼴이고 앱 수에 비례해 늘지 않는다**는 걸 세 번의 실측으로 확인했다.

**Redis 부하도 줄었다.**

| 지표 | 전환 전 | 지금 | 변화 |
|---|---|---|---|
| 연결 수 | 7,475 | 4,606 | -38% |
| 명령 처리율 | 78,815/s | 10,699/s | -86% |
| 아웃바운드 | 4.7 MB/s | 0.56 MB/s | -88% |

여기서 원인을 나눠 봐야 한다. **명령 처리율 감소는 대부분 통합이 아니라 버그 수정 덕이다.** 초당 856개의 잡이 3번씩 실패하던 게 멈췄다. 반면 **연결 수 2,869개 감소는 통합의 몫**이다. 연결은 잡 양이 아니라 프로세스 수에 비례하는데 앱별 컨테이너 40개가 사라졌다. 앞으로 앱을 더 얹어도 연결 수는 안 늘어난다. 공용 prefix 소비자는 통합 워커 하나뿐이다. 이게 메모리 회수보다 오래가는 이득이다.

아웃바운드 4.7 → 0.56 MB/s는 월 12.4TB가 1.5TB로 줄었다는 뜻이다. 과금 대상이라 그만큼 요금이 빠진다.

**드레인 계약도 운영에서 실증됐다.** LB 헬스체크 경로를 앱별 경로에서 `/health/lb`로 바꾸고 재기동 중에 0.5초 간격으로 쐈다.

| | 이전 | 지금 |
|---|---|---|
| 실패율 | 23% (60회 중 14회) | 0.65% (773회 중 5회) |
| 실패 성격 | 연결 끊김. LB가 죽은 컨테이너로 보냄 | 503. LB가 타깃이 빠진 걸 알고 응답 |

35배 개선인데, 실패의 성격이 달라진 게 더 중요하다. 콜드 스타트는 재기동 직후 1회차가 0.14초, 2·3회차는 0.066초로 내려간다. 테넌트가 처음 접촉할 때 스키마 컴파일과 DB 연결이 일어나는 비용이고 그 뒤로는 앱 수와 무관하게 일정하다.

남은 앱 4개는 1단계(워커만 전환)까지 올려 뒀다. LB flip은 개발자들이랑 상의해서 한 번에 진행할 예정이다.

## 배운 것

- **재기 전에는 문제를 잘못 짚는다.** 2GB 상한이 문제라고 믿고 시작했는데 실제 범인은 고정비였다. 상한만 줄였으면 아무것도 나아지지 않았을 거다. 나중에 상한을 실제로 낮춰 보고 메모리가 1MB도 안 줄어드는 걸 보면서 확실히 알았다.
- **한 층을 고치면 다음 층이 드러난다.** 프로세스를 합쳐도 큐 소비자는 그대로였고, 큐를 합치고 나서야 보름 전부터 실패하던 잡이 보였다. 병목은 한 번에 하나씩만 보인다.
- **숫자가 좋아졌다고 내 덕은 아니다.** Redis 명령이 86% 줄었을 때 통합의 성과인 줄 알았는데, 뜯어 보니 대부분 따로 고친 버그 덕이었다. 통합의 몫은 연결 수 감소였다. 지표가 좋아지면 원인을 나눠 봐야 한다.
- **합치면 사고의 반경이 달라진다.** 앱별로 떠 있을 때는 한 앱이 죽어도 나머지가 멀쩡했다. 합치고 나니 부팅 훅 하나, 경로 충돌 하나가 전 테넌트를 죽인다. 격리가 사라진 자리를 가드와 spec으로 메워야 했다.
- **느려졌을 때 제일 먼저 의심받는 건 방금 바꾼 것이다.** 통합 때문이라고 확신하고 며칠을 봤는데 범인은 통화 상태 조회였다. 바꾼 것부터 의심하는 건 맞지만, 재 보기 전에는 결론을 내리면 안 된다.
