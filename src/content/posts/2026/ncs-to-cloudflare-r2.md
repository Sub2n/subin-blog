프론트엔드 개발자로 일하면서 저장소랑 CDN, DNS를 직접 만진 건 이번이 처음이다. 9월 14일부터 18일까지 5일 동안 했고, 결정은 전부 내가 했다. 뭘 보고 뭘 골랐는지 남겨 둔다.

## 이전 환경

- 이미지랑 영상은 네이버 클라우드 스토리지(NCS)에 올리고 `cdn.pixelteam.io`로 서빙했다.
- 썸네일은 자체 이미지 프록시 서버(proxy-v4)가 만들었다. 리사이즈, 스마트 크롭, YuNet으로 얼굴 검출 크롭까지 전부 여기서 처리하고, 변환 결과는 NCS 캐시 버킷에 쌓았다.
- 앱 45개가 이 구조를 같이 쓴다.

## 뭐가 문제였나

proxy-v4 호스트 운영비랑 NCS 전송비가 매달 나갔다. 썸네일 바이트가 전부 NCP 인터넷 아웃바운드로 과금되고 있었다.

그런데 확인해 보니 좀 아까운 상황이었다. proxy-v4 도메인이 Cloudflare DNS를 쓰면서도 프록시(주황 구름)가 꺼져 있었다. 응답에 `immutable` 캐시 헤더까지 이미 보내고 있었는데, 그걸 받아 줄 엣지가 없었던 거다. 캐시하라고 다 말해 놓고 아무도 안 듣는 상태.

거기에 사용자의 80% 이상이 해외인데 원본도 썸네일도 전부 서울에서 나가고 있었다.

## 처음 생각한 것

- 신규 업로드부터 R2로 보내고, 기존 객체는 서비스 단위로 `rclone copy`. 도메인은 새로 `cdn.pixels.im`.
- 썸네일은 Cloudflare 이미지 변환(`/cdn-cgi/image/`)으로. 얼굴 크롭만 proxy-v4에 남길지는 `gravity=face`랑 결과를 대조해 보고 정한다.
- 운영 DB의 이미지 URL을 건드려야 하니까 여기는 진짜 조심해서. 도메인 제거는 다 옮기고 맨 마지막에.

## 비용부터 재 봤다

계획을 더 짜기 전에 숫자를 먼저 보고 싶었다. NCS 버킷을 읽기 전용으로 전수 조사했다.

- 원본 객체 106만 개, 451GB. 최근 30일 신규만 17만 개.
- 프록시 캐시 객체 182만 개, 376GB. 6개월치가 이만큼 쌓여 있었다.

계산해 보니 R2 저장비는 월 $7 수준이었다. 생각보다 너무 싸서 한 번 더 확인했다. 결국 **저장소 비용은 무시할 수준이고 전환 판단은 변환 비용이 좌우한다**는 결론이 나왔다.

Cloudflare 변환은 월 고유 변환(원본 × 옵션) 1,000건당 $0.50이다. 손익분기가 월 약 145만 건인데, 캐시 버킷 실측으로는 월 신규 고유 변환이 28만 건. 여유로워 보이지만 함정이 있다. Cloudflare는 월 단위로 다시 세기 때문에 옛 이미지 재조회분이 계속 얹힌다. 상한으로 잡으면 182만 건까지 갈 수도 있다.

그래서 소형 앱 하나로 7일 파일럿을 돌려서 실제 고유 변환 수를 재고 확대하기로 했다. 여기서 숫자 하나로 방향이 갈릴 수 있으니까.

## 얼굴 크롭, gravity=face로 갈 뻔했다

14일 실험에서는 `gravity=face`가 실사 얼굴을 잘 잡길래 그걸로 확정했다. 그런데 16일 운영 파일럿에서 문제가 나왔다.

선이 단순한 애니 얼굴에서 얼굴을 아예 못 잡고 center 크롭으로 떨어졌다. 사이타마 포스터로 테스트했는데 기존 YuNet은 잘만 잡던 이미지였다. 이미 확정한 결정이 파일럿에서 뒤집히는 경험을 여기서 했다.

네 가지 방식을 한 화면에 놓고 비교했다.

1. 원본
2. 기존 proxy-v4 (YuNet)
3. Cloudflare `gravity=face`
4. 서버에서 YuNet으로 얼굴 좌표를 한 번 구해 저장하고 Cloudflare에 `gravity=XxY`로 넘기기

4번은 너무 잘리는 경향이 있었다. 대신 얼굴 박스로 프리셋 비율의 크롭 창을 계산해서 `trim=상;우;하;좌`로 넘기고, 얼굴 중심을 창 높이 40% 지점에 두니까 proxy-v4 결과랑 똑같이 나왔다. 이걸로 갔다.

- 검출은 업로드 후 워커가 1회. `onnxruntime-node` + YuNet 2023mar. 프리빌트 바이너리가 들어 있어서 빌드 스크립트 없이 그냥 돌았다. 여기는 운이 좋았다.
- 박스는 호스트 무관 객체 키로 저장한다. NCS랑 R2가 같은 객체를 같은 키로 갖고 있어서, URL로 잡으면 같은 이미지를 두 번 검출하게 된다.
- 박스가 없는 이미지(기존 이미지, GIF, 검출 실패)는 `gravity=face`로 폴백. 백필은 안 했다.

이렇게 해도 트래픽은 Cloudflare가 받는다. proxy-v4를 타지 않고 검출은 이미지당 한 번뿐이라 비용 이점이 사라지지 않는다는 걸 확인하고 진행했다.

중간에 이게 오버엔지니어링 아닌가 싶어서 한 번 물어봤다. 얼굴 크롭 사용처가 4곳뿐인데 그중 게시판 타임라인이 물량이 커서 그냥 버릴 수가 없었다.

## 앱별 토글을 만들었다가 사흘 만에 지웠다

- **15일**: 배포 플래그 대신 어드민 앱 관리에서 앱마다 저장소(NCS/R2)랑 썸네일 변환을 켜고 끄는 AppConfig 토글을 만들었다. 문제 생기면 앱 하나만 되돌리려고.
- **17일**: 운영 앱 45개를 하나씩 켜기가 너무 귀찮았다. 서버 env 기본값을 두고 앱별 값이 있으면 그게 우선하는 3상태로 바꿨다.
- **18일**: 전부 켜고 나니 이 설정이 남아 있을 이유가 없었다. 세 개 다 지우고 상시 on으로 고정했다. 저장소는 env `STORAGE_PROVIDER` 하나만 본다.

되돌리기 수단으로 만든 게 사흘 만에 잔재가 됐다. 전환 기간에만 필요한 스위치였는데, 그때는 이게 오래 갈 설정인 줄 알았다. 이런 건 만들 때부터 수명을 생각해야 한다는 걸 배웠다.

## 막혔던 것들

여기부터는 하나하나가 다 하루씩 잡아먹은 것들이다.

**CORS.** 계획서에 R2 CORS를 `AllowedHeaders: ["Content-Type"]`로 적어 놨는데, 클라이언트 업로드가 rxjs `ajax.put`을 쓰면서 `x-requested-with`를 자동으로 붙이고 있었다. NCS는 `*`라서 지금까지 드러나지 않았던 거다. 그대로 컷오버했으면 웹이랑 웹뷰 업로드가 전부 실패했을 거다. 정찰에서 잡아서 다행이었다.

**시크릿.** R2 자격증명을 `.env.dev`에 넣고 커밋하려다 막혔다. GitHub 시크릿으로 옮기고 배포 워크플로가 주입하게 했는데, 그 주입 스텝이 시크릿이 비어 있으면 경고만 찍고 그냥 넘어갔다. 결과적으로 이미지에는 "R2 써라"만 있고 키가 없어서 dev API가 부팅에서 죽었다. 경고만 찍고 넘어가는 건 위험하다.

**R2 재작성 규칙.** 코드는 키를 `cdn/<service>/<key>`로 저장하는데 R2 커스텀 도메인은 키를 경로 그대로 노출한다. `/cdn`을 붙이는 Transform Rule이 없으면 업로드한 게 전부 404다. 이건 미리 알아서 넘어갔다.

**변환 Sources.** 이미지 변환 허용 목록에 옛 호스트만 넣고 새 호스트를 안 넣어서, R2에 올라간 새 이미지의 변환 URL이 전부 403이었다. 파일럿 앱에서 새 이미지가 죄다 플레이스홀더로 보였다.

**구 워커.** R2 URL을 외부 이미지로 판정하는 옛 코드가 돌던 워커가 R2 게시글을 자동으로 블라인드했다. 이거 원인 찾느라 며칠 걸렸다. 한 번은 다른 머신의 test 워커, 한 번은 내 맥에 떠 있던 옛 `api:serve` 프로세스였다. 둘 다 dev DB랑 Redis를 공유하고 있었다. 내 로컬 프로세스가 dev 데이터를 건드리고 있을 거라고는 생각도 못 했다.

**purge.** 이미지를 지우면 원본 URL은 2초 안에 엣지에서 사라지는데 변환본(`/cdn-cgi/image/...`)은 계속 남았다. 프리셋 조합 URL을 같이 purge하도록 만들었는데, 실측해 보니 그것도 안 지워졌다. Cloudflare 문서를 다시 읽으니 "cdn-cgi URL은 purge할 수 없다"고 적혀 있었다. 문서에는 "원본을 purge하면 최적화본도 같이 지워진다"고도 써 있는데, 실측은 그렇지 않았다. 결국 변환본 Edge TTL을 1일로 낮추는 Cache Rule로 대응하고 purge 코드는 뺐다.

**Cache-Control.** 기존 CDN 응답에 Cache-Control이 아예 없어서 브라우저가 휴리스틱 캐시에 의존하고 있었다. 이건 CDN 설정이 아니라 객체 메타데이터라서 업로드 시점에만 넣을 수 있다. 서명 URL 응답에 값을 돌려주고 클라이언트가 PUT 헤더로 싣게 했다. 그 전에 R2 버킷 CORS에 `Cache-Control` 허용부터 추가해야 한다.

**404 캐시.** 프록시 nginx가 `add_header ... always`로 오류 응답에도 30일 캐시 헤더를 붙이고 있었다. 없는 이미지의 404가 엣지에 30일 남는다는 뜻이다. 업로드 직후 잠깐 404였던 이미지가 그대로 굳을 수 있었다.

**한글 파일명.** DB URL 치환 워커가 아이돌 이미지 221건을 "R2에 없음"으로 잡았다. 객체는 양쪽에 UTF-8 키로 멀쩡히 있는데 URL은 퍼센트 인코딩돼 있어서 HEAD 키가 어긋난 거였다. 디코딩 한 줄로 끝났다.

**비교 상수.** 기본 프로필 이미지 URL 같은 상수를 코드가 `===`로 비교하고 있었다. DB 값만 치환하면 추천 필터랑 모더레이션 판정이 조용히 깨진다. 상수 목록은 치환에서 제외했다. QA가 잡아 준 건데 이건 못 찾았으면 운영에서 터졌을 거다.

**Redirect Rule 한도.** 옛 도메인 301을 걸다가 플랜 한도에 걸렸다. 이런 건 미리 알 방법이 없다.

## 이관 순서

- **Phase A**: 코드가 두 저장소를 다 알게. 삭제랑 조회는 양쪽 다.
- **Phase B**: Cloudflare 대시보드 작업. 토큰, 커스텀 도메인, 재작성 규칙, 캐시 규칙, CORS.
- **Phase C**: 신규 업로드를 R2로 컷오버. dev에서 하루 소크하고 prod.
- **Phase D**: 썸네일 URL 빌더를 Cloudflare 변환으로. 파일럿 앱 하나부터.
- **Phase E**: 기존 객체 `rclone copy`. 용량 기준으로 큰 앱 두 개가 76%를 차지해서 작은 앱부터.
- **Phase F**: DB URL 호스트 치환. dry-run으로 센 대상이랑 write가 실제로 손대는 대상이 같은지 spec으로 고정했다. 새 URL은 R2에 HEAD로 먼저 확인하고, 원본 값을 조건으로 건 update로 쓴다.

Phase E를 돌리다가 재밌는 걸 알았다. 이관 작업을 돌린 서버가 NCP 안이 아니라 NCS 이그레스 요금이 붙고 있었다. NCP VM에서 돌리면 같은 리전 내부 트래픽이라 무료다. 같은 국내 서버인데 왜 요금이 다른지 한참 이해가 안 갔다. 프론트엔드에서는 볼 일 없던 요금 구조였다.

## API도 Cloudflare 뒤로 넣었다

같은 주에 별도 워크트리에서 API를 Cloudflare 프록시 뒤로 넣는 작업도 같이 했다.

HAR 파일을 분석했더니 예상과 다른 결과가 나왔다. **서울에서는 Cloudflare 엣지가 오리진 직결보다 느렸다.** 한국 트래픽이 홍콩 PoP로 간다. 그래도 사용자의 80%가 해외라 진행하기로 했다.

그 전에 오리진부터 손봤다. API 응답 압축이 아예 없었다. zstd/br/gzip 협상을 넣으니 10.7KB JSON이 424B가 됐다. 이 차이를 보고 좀 허탈했다. 그동안 비압축으로 태평양을 건너다니고 있었던 거다. ETag도 붙여서 재요청은 304로 끝나게 했다.

엣지 캐시 헤더는 익명 GET에만 붙였다. Authorization이 있으면 `private, no-store`. 이 코드베이스의 `@Public()`은 "익명 허용"이지 "익명이랑 같은 응답"이 아니라서, 잘못 캐시하면 개인화된 응답이 남한테 나간다. 여기가 제일 무서웠다.

신뢰 프록시 대역도 넣어야 했다. Cloudflare를 거치면 서버가 보는 접속 IP가 Cloudflare가 되니까, `X-Forwarded-For`를 믿을 대역 목록이 필요하다. 그런데 확인해 보니 이 값이 지금까지 prod에서 계속 비어 있었다. compose가 root ssh heredoc으로 돌아서 호스트 셸 변수가 전달이 안 되고 있었다. 즉 지금까지 `request.ip`가 nginx IP로 찍히고 있었다는 뜻이다. 이번 작업이랑 별개로 원래 고장 나 있던 셈이다.

배포하고 나서는 `@fastify/compress`가 webpack `runtimeDependencies`에서 빠져서 dev 전 앱이 크래시 루프에 빠졌다. 런타임 패키지 spec에 필수 항목으로 넣어서 다시 빠지면 잡히게 했다.

Cache Rule이 안 먹는 줄 알고 규칙을 몇 번이나 뜯어봤는데, 알고 보니 `curl -I`가 HEAD 요청이라 GET 조건에 안 걸린 거였다. 이건 교훈 문서에 따로 적어 뒀다.

앱별로 켜려고 어드민 토글이랑 CLI 스크립트까지 만들었는데, 확인해 보니 `*.pixelteam.io` 와일드카드가 이미 프록시 상태라서 prod API 45개가 전부 Cloudflare를 거치고 있었다. 만들어 놓고 나서 안 게 좀 허무했지만, 그냥 전부 켠 상태로 가기로 했다.

어드민 토글도 순탄하지 않았다. 처음엔 "조회 실패"로 떴는데 purge용 존 ID를 DNS 조회에도 써서 엉뚱한 존을 뒤지고 있었다. 존 ID를 분리했다. 그랬더니 이번엔 "레코드 없음"으로 떴다. 와일드카드로 받고 있어서 개별 레코드가 아예 없었던 거다. 개별 레코드가 없으면 와일드카드 값을 보여 주고, 끌 때만 개별 레코드를 만들게 바꿨다.

16일에 다시 재 봤더니 서울 회귀가 +350~650ms였다. 계획 단계에서 예상한 +70ms이 아니었다. 국내 비중이 큰 앱 13개는 직결로 되돌리는 걸 검토 중이다.

## 지금 구조

- 신규 업로드는 R2로 간다. 클라이언트가 presigned PUT으로 직접 올리면서 Cache-Control 헤더를 같이 싣는다.
- 썸네일은 우리 CDN 원본이면 항상 Cloudflare 변환을 탄다. 원본 호스트는 R2로 치환해서 Cloudflare가 NCS에서 원본을 받아 가지 않게 했다. 외부 호스트 이미지는 변환 없이 원본 그대로.
- 얼굴 크롭은 서버 YuNet 1회 검출 + `trim`. 박스가 없으면 `gravity=face`.
- 삭제하면 원본 URL을 purge하고, 변환본은 Edge TTL 1일로 알아서 빠진다.
- 클라이언트는 이제 proxy-v4 URL을 만들지 않는다. 역파서만 남겼다. 옛 공유 링크랑 구버전 앱이 만든 URL을 원본으로 풀어야 해서 이건 지울 수가 없다.
- proxy-v4 서버는 호출이 0이 되면 내린다. NCS는 Phase F가 끝난 뒤에.

## 남은 것

- Phase F를 큰 앱 두 개까지 끝내고 옛 도메인 301 마무리.
- proxy-v4 호출이 0인지 확인하고 서버 내리기.
- 국내 비중 큰 앱의 API 프록시를 끌지 말지 결정.
- 파일럿 7일치 고유 변환 수로 비용 다시 확인.
