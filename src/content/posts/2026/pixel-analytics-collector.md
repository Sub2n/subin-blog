9월 7일에 시작해서 18일에 마무리했다. 시작할 때 나는 API도 서버도 Docker도 클라우드도 모르는 프론트 개발자였다. 이번에 한 세 가지 작업 중 제일 먼저 손댄 거라 제일 많이 헤맸고, 그만큼 제일 많이 배웠다.

## 왜 만들었나

우리는 앱을 50개 넘게 운영하는데, 이벤트는 GA랑 Amplitude 두 군데로만 보내고 있었다. 클라이언트 진입점은 `emitLogEvent()` 하나, 서버는 푸시 보낼 때만 GA를 썼다.

문제는 보고 싶은 걸 못 본다는 거였다.

- 앱별, 유저별 실시간 지표를 우리 어드민에서 볼 수가 없다. 원본 조회도 안 되고 사용자 단위 추적도 안 된다.
- 탈퇴, DM·그룹챗 생성, 채팅방 참여자 수, 푸시 도달, 포그라운드 푸시 수신. 이건 GA에 아예 없는 지표다.
- Firebase는 완전한 데이터가 이틀 뒤에 나온다. Amplitude BigQuery export는 누락도 있다.

그래서 방향은 이렇게 잡았다. 수집만 제대로 되면 기획자는 DB에 MCP로 붙어서 보면 되고, GA로 되는 건 GA에서 보고, 거기서 안 되는 것만 화면을 따로 만든다. 수집이 먼저다.

## 처음 원한 것

- GA랑 똑같이 수집하는 게 1차 목표. 대시보드는 2차.
- 수집기는 모든 프로젝트랑 API에서 독립적이어야 한다. 앱이 전부 죽어도 수집기는 멀쩡해야 한다.
- 프로젝트마다 수집기를 띄우는 게 아니라, 수집기 하나에 프로젝트 키를 넘겨서 쌓는다.
- 스택은 Rust, Redis, MongoDB, Docker. API는 큐에 넣고 바로 리턴하고, 워커가 Redis에서 꺼내 Mongo에 bulk write.

우선순위는 확실했다. 수집만 되면 대시보드는 언제든 원하는 모양으로 만들 수 있으니까.

## 설계

그려 놓고 보니 이렇게 됐다.

클라이언트 → Rust axum API(검증하고 Redis에 `XADD` 한 다음 바로 204) → 전용 Redis Streams → 워커(`insert_many`, sessions·devices·users upsert, 일/주/월 집계, BigQuery 스토어 잡) → 전용 Mongo.

몇 가지는 처음부터 못 박고 갔다.

- **유실 방어를 세 겹으로.** 클라이언트 localforage 재전송, API 디스크 스풀, Redis PEL.
- **수집 엔드포인트는 무인증.** appKey 검증이랑 레이트리밋만 건다. GA랑 같은 모델인데, 인증을 걸면 비로그인 first_open이랑 로그인 화면 분모가 통째로 날아간다. 서버에서 수집기로 보낼 때만 공유 시크릿 헤더.
- **Mongo time-series는 포기.** unique 인덱스가 안 돼서 멱등이 깨진다.
- **계약은 fixture 하나로.** `libs/universal`에 JSON 하나 두고 TS spec이랑 Rust 테스트가 같이 읽게 했다. 언어가 다른 두 구현은 이렇게 묶어야 안 어긋난다.
- **보존은 hot 90일, 아카이브 3년.** 전날치를 gzip NDJSON으로 R2에. txt 대신 NDJSON gzip으로 하면 10배 압축되고 나중에 다시 밀어 넣을 수도 있다.

그리고 내가 직접 눈으로 확인할 수단을 꼭 넣고 싶었다. GTAG처럼 콘솔에 `[COLLECTOR]` 로그가 찍히게 하고, `/v1/debug/summary`도 만들었다. 내가 못 보는 시스템은 못 믿겠더라.

첫 커밋에서 10k events/s에 p99 8.22ms, 유실 0/800. 여기까진 순조로웠다.

## Docker부터 배웠다

"docker가 뭐고, docker를 클라우드에 올리면 클라우드 서버에서 만들어지는 건지, 이미지는 아무 데서나 만들어둬도 되는 건지." 진짜 이 수준에서 물어봤다. 정리하면 이랬다.

- 서버는 항상 켜져 있는 남의 컴퓨터
- 이미지는 nx build 산출물을 zip으로 묶은 것. 어디서 만들든 상관없다
- ghcr은 이미지용 npm 레지스트리
- compose는 package.json의 scripts

이해하고 나니 좀 허무할 정도로 간단했는데, 실제로 돌리는 건 또 다른 얘기였다.

**glibc.** 첫 빌드에서 워커가 `GLIBC_2.38 not found`로 재시작을 무한 반복했다. 빌더 이미지가 새 Debian으로 올라갔는데 런타임은 옛 버전이라 그랬다. `rust:1-slim-bookworm`으로 고정해서 해결. 이때 배운 게 "컨테이너가 떴다"랑 "다 떴다"는 다르다는 거다. `docker ps`에 보인다고 살아 있는 게 아니었다.

**CI.** Mac 러너에는 docker가 없고, 러너 체크아웃에는 node_modules가 없어서 `npx nx`가 안 돌았다. 수집기 배포만 Linux 러너로 떼어냈다.

**시크릿.** 이미지에 시크릿 굽는 건 막혔다. private repo고 다른 키도 전부 정적으로 쓰고 있어서 env 파일을 커밋하기로 했다. 좋은 방법이 아닌 건 아는데, 지금 구조에서 여기만 다르게 할 이유도 없었다.

**운영 스위치.** 이게 좀 아찔했다. 운영 수집기가 아직 없는데 main이 나가면 수백만 기기가 없는 주소로 재시도를 때린다. 계약에 phase 스위치를 넣고 prod는 false로 시작했다.

**LB 헬스체크.** 전용 서버를 받아서 dev랑 prod 수집기를 한 대에 올렸다. TLS는 LB가 처리하고 api는 평문 포트를 직접 받는 구조. 그런데 LB가 `/`를 계속 치는데 503이 났다. `/`에도 200을 주게 했다.

**바인딩.** "api가 127.0.0.1:14000이어야 하는 거 아냐?"라고 물었다가 배웠다. LB는 사설망으로 들어오니까 0.0.0.0이어야 한다.

**ssh랑 콘솔은 별개.** 서버에는 붙을 수 있는데 LB랑 ACG랑 DNS는 왜 내가 직접 못 하는지 한참 헷갈렸다. 그건 콘솔 권한이었다.

DNS가 LB로 붙자마자 dev 웹 앱 실트래픽이 자동으로 들어오기 시작했다. 로그에 실제 이벤트가 찍히는 걸 보는 순간이 이 작업에서 제일 좋았다. 지금 켜도 안전하다길래 prod도 바로 켰다.

## 유실 0을 목표로

9일에 1순위를 다시 분명히 했다. 모든 앱에서 프로젝트별로 지표가 빠지거나 유실되지 않을 것. 그러고 나서 파고들었더니 구멍이 꽤 나왔다.

- `XADD MAXLEN ~200000`이 아직 ACK 안 된 항목까지 잘라내는 경로가 있었다. 백프레셔가 걸리면 스풀로 전환하고, 워커가 ACK된 것만 `XTRIM MINID`로 지우게 했다. MAXLEN 200만은 안전망으로만 남겼다.
- 400으로 거절한 건 DLQ에 원문이랑 사유를 남기게 했다. 안 그러면 뭐가 왜 안 들어왔는지 영영 모른다.
- 레이트리밋을 600에서 6000/min/IP로 올렸다. 5초 배치면 사용자 한 명이 분당 12건 이하라 600은 너무 빡빡했다.
- 클라이언트 큐 2000 → 5000, 버린 건 로그로.
- 그러다 **appKey를 주입 안 해서 한 건도 못 보내고 있던 내부 앱 8개**를 발견했다. 이건 좀 아찔했다. 전수 spec을 붙여서 다시는 조용히 빠지지 않게 했다.

사용자 속성도 바꿨다. 원래는 호출마다 이벤트로 남기고 있었는데, GA는 속성만 바꾸고 이벤트를 안 남긴다. GA랑 똑같이 가는 게 1차 목표니까 users랑 devices에 최신값만 두는 쪽으로.

## 전용 서버에 아무것도 없었다

전용 서버를 열어 봤더니 백업 cron이 어디에도 없었다. 감시도 없었다. 04:00 백업이랑 5분 watchdog을 넣었는데, 넣고 나서 또 줄줄이 터졌다.

- 백업 경로에 phase가 없어서 prod 덤프가 dev를 덮어 버렸다.
- `$HOME` 기준이라 root cron이랑 watchdog이 서로 다른 데를 보고 있었다.
- `rsync --delete`가 watchdog 상태 파일을 지웠다.
- 호스트 설치 스크립트를 다시 돌리면 무조건 docker 데몬을 재시작해서 dev·prod 컨테이너가 전부 내려갔다. 그날 측정한 게 다 무효가 됐다.

백업 넣다가 서비스를 내리는 게 좀 웃기면서도, 이런 게 인프라구나 싶었다.

"이렇게 하면 DB 터지는 일은 없겠지?"를 물어봤더니 모든 단계의 상한 표가 나왔다. TTL, XTRIM, 스풀 2GiB, 클라 큐 5000. 결국 진짜 위험한 건 디스크 하나더라. 그래서 dev에서 실제로 재 봤다.

- events 문서 하나가 404B인데, 그중 인덱스가 220B다. 데이터(100B)보다 인덱스가 크다. 이 숫자를 보고 좀 놀랐다.
- 하루 100만 건 가정하면 events 90일에 29GB, sessions 365일에 62GB.
- sessions TTL을 90일로 줄이고, planner가 안 쓰는 인덱스 3개를 뺐다. 이벤트당 110B → 70B.

그러다 별건으로 하나 더 잡았다. 30분마다 도는 오늘 집계가 `appKey` 없이 조건을 걸어서 매번 COLLSCAN이었다. `{phase, ts}` 인덱스 하나 넣으니 88ms가 4ms가 됐다. 이런 건 볼 때마다 기분이 좋다.

## 아카이브가 안 돈 줄 알았다

첫 prod 아카이브가 안 돈 것처럼 보였다. 기록도 없고 R2에 파일도 없고, 컨테이너를 재기동해 버려서 옛 로그까지 날아갔다. 모든 종료 경로에 기록을 남기고 수동 CLI를 만들고 나서야 원인이 잡혔다. prod 이벤트가 전부 전전날 것이고 전날은 0건이라 "할 일 없음"으로 끝난 거였다. 그 경로만 기록을 안 남기고 있었다.

여기서 교훈 하나. 재기동 전에 컨테이너 로그는 무조건 파일로 남겨 놓자.

그리고 담당이 한 말이 계속 머리에 남는다. "아무것도 안 들어오는 상태가 가장 건강해 보인다." 맞는 말이라 24시간 수집량이 임계 밑으로 떨어지면 경고하게 만들었다.

## 한 호스트에 다 있는 게 마음에 걸렸다

API, 워커, DB, Redis가 전부 한 호스트에 있었다. 이건 아무래도 아니다 싶어서 DB랑 Redis를 외부로 빼고 Tailscale로 붙기로 했다. 인프라팀이 외부 Mongo 인스턴스를 dev·prod 따로 내줬다. Redis는 api랑 worker 사이의 큐라 앱 호스트에 두고 requirepass만 걸었다.

옮기는 과정은 이랬다.

워커 세우고, dump/restore 파이프로 넘기고, 건수를 대조했다. dev events 83,336건 정확히 일치. 이 숫자 맞는 걸 확인했을 때 안심이 됐다.

물론 여기서도 걸렸다.

- compose YAML 폴드랑 `sh -c` 개행 때문에 `exec redis-server`만 실행돼서 requirepass가 안 걸렸다. 몇 분 동안 api·worker 접속이 실패했는데, 스풀 덕분에 유실은 0이었다. 세 겹으로 만들어 둔 게 이럴 때 값을 한다.
- env 값에 있던 `&`가 `source`에서 백그라운드 실행으로 해석됐다. 단일따옴표로 해결.
- 기획자가 붙는 계정이 prod 인스턴스에 등록이 안 돼 있어서 인증이 계속 실패했다. 등록 스크립트를 다시 돌렸다.

"수집기 api에서 DB로 바로 쏘면 안 되고 워커로 넘기고 바로 리턴해야 한다"고 걱정했는데, 확인해 보니 이미 그 구조였다. 400/403/413/429/503이 각각 언제 나는지 표로 받고 나서야 마음이 놓였다.

## 대시보드가 자꾸 dev를 봤다

어드민 대시보드가 dev 데이터를 보고 있었다. 전송용이랑 분리해서 대시보드 전용 수집기 URL을 두고, env 4개가 prod를 가리키는지 spec으로 고정했다.

그랬는데 "아직 dev로 뜨는데?" 뱃지가 수집기 응답이 아니라 어드민 자기 환경을 찍고 있었다. 응답의 phase를 읽게 고쳤다.

그랬더니 이번엔 "뱃지만 prod고 데이터는 dev". BFF의 Redis 캐시 키에 수집기 host가 없어서 TTL 동안 옛 응답이 그대로 나가고 있었다. 실시간만 30초 캐시라 뱃지가 먼저 바뀐 거였다.

같은 증상으로 세 번을 왔다 갔다 했다. 결론은 하나다. 데이터 출처는 응답에서 읽어야지, 내 환경에서 짐작하면 안 된다.

## 열흘 뒤에 21시간 구멍을 발견했다

17일에 prod 데이터 1,860만 건, 31개 앱 3플랫폼 유입, 일 집계랑 원본이 일치하는 걸 확인했다. 잘 되고 있구나 했는데, 13일 쪽에 구멍이 있었다.

시간당 12~17만 건이 들어오던 게 0.7만으로 떨어져 있었다. 약 21시간, 200만 건. 서버 이벤트는 거의 전량이 날아갔다.

원인을 따라가 보니 12일 02:30 아카이브였다. 가장 큰 앱(178만 건) 차례에서 하루치를 String으로 통째로 푸는 코드가 있었다. 1GB가 넘는다. 8GB짜리 호스트가 응답 불능이 됐고, 이 호스트는 앱 워커 15개랑 공유하고 있었다. 다음 날 재부팅으로 겨우 살아났다.

내가 만든 백업 잡이 서비스를 죽이고 데이터를 날렸다는 게 제일 뼈아팠다.

그래서 줄 단위 스트리밍으로 바꾸고, 같이 나온 것들도 손봤다.

- 늦게 도착한 서버 이벤트(14.7만 건이 20시간 뒤에 도착)가 01:10 마감 후에 오면 일 집계에서 영영 빠졌다. D-1~D-3 재계산으로.
- 서버 전송 재시도가 3번 × 5초였다. 수집기가 15초만 죽어도 영구 실패라는 뜻이다. 2분 간격 24시간으로.
- `setUserId(undefined)` 때문에 userId 키가 사라져서 첫 실행 배치가 통째로 거절당하고 있었다. DLQ에 585건. null로 고정.
- 사용자 속성 6종이 Observable 미구독이라 GA에 아예 안 가고 있었다. 이것도 이번에 발견.
- 서버 이벤트가 전부 `appVersion=unknown`이었다. SENTRY_RELEASE 주입.

## 앱 워커에 의존하면 안 된다

가장 큰 앱의 워커가 Node 힙 고갈로 죽지도 못한 채 20시간을 버텼다. `restart: always`는 안 떴고, BullMQ lock 갱신은 계속 실패했다. 그 앱의 서버 이벤트가 최대 43시간 늦게 도착했다. 수집기 쪽은 멀쩡했는데도.

서버 이벤트를 앱 워커의 BullMQ 잡으로 보내던 게 원인이었다. 앱 워커에 수집기가 의존성을 가지면 안 된다. 이벤트가 생긴 프로세스가 수집기 API를 직접 부르게 바꿨다.

- 메모리 버퍼 200건/5초.
- 재시도 예산 8MB → 64MB(약 8만 건). 이제 BullMQ가 뒤를 안 받쳐 주니까 이 큐가 유일한 완충이다.
- 배포 순서가 중요하다. API 먼저 올려서 큐에 잡을 더 안 넣게 하고, Bull Board에서 waiting이 0이 된 다음에 워커. 워커를 먼저 올리면 큐에 남은 배치가 처리가 안 된다.

"새 GA 이벤트 추가할 때 수집기도 같이 심는 규칙 저장돼 있지?"라고 물었더니 절반만 돼 있었다. 스킬에 규칙을 명시하고, Firebase 직접 호출이나 미구독 setUserProperty를 실패시키는 spec을 붙였다. 사람이 기억하는 규칙은 언젠가 빠진다.

## 백필

14일 집계 백필을 돌리는데 떠 있는 워커랑 백필 프로세스의 확인용 HTTP 포트가 겹쳐서 `Address already in use`로 바로 죽었다. 죽은 줄도 모르고 있다가 나중에 알았다. `-e PORT=4500`으로 비켜 주고 다시. 그리고 백필 프로세스는 다 끝나도 워커로 남아 있어서 호스트에서 직접 내려 줘야 한다.

돌리고 나니 숫자가 확 달라졌다. 가장 큰 앱의 14일 친구신청이 179에서 13,687로, DAU가 2,057에서 2,854로. 빠져 있던 게 이만큼이었구나 싶었다.

## 지금 구조

- **클라이언트**: `emitLogEvent()` 한 번 부르면 Amplitude, 수집기, GA로 다 간다. 20건/5초 배치, sendBeacon, 오프라인 큐 5000, 세션 30분.
- **서버**: 앱 프로세스가 수집기 API를 직접 호출한다. 기다리지 않고, 메모리 버퍼랑 64MB 재시도 큐가 받친다.
- **수집기**: api(검증·XADD·스풀 2GiB·레이트리밋) → 전용 Redis Streams → worker(insert_many, DLQ, 01:10 일 집계 D-1~D-3, 30분마다 오늘 갱신, 02:30 R2 아카이브, 05:00 스토어 잡) → 외부 Mongo.
- **보존**: events 90일 뒤 R2로 3년, sessions 90일, 집계·devices·users는 영구. 04:00 백업, 5분마다 watchdog이 큐·DLQ·지연·백업·아카이브·디스크 예상일·24시간 수집량을 본다.
- **보는 사람**: 기획자는 Tailscale에 읽기 전용 계정으로 붙어서 MongoDB MCP나 Compass로 원본까지 본다. 어드민 `/analytics?project=`는 항상 prod를 읽는다.

## 남은 것

- perf 지표에서 제외한 표본 수를 사유별로 집계해야 한다. 지금은 느려질수록 지표가 좋아 보이는 편향이 있다.
- Play 스토어 설치 수가 BigQuery에서 계속 0행이다. Play Console 내보내기 연결부터 확인해야 한다.
- 클라이언트 수정(userId null 고정, 사용자 속성 구독)은 스토어 반영이 돼야 적용된다. 그때까지 DLQ에 첫 실행 배치가 계속 쌓인다.
- 앱 워커 힙 고갈 자체는 별도 과제다. 두 번째로 큰 앱도 같은 경로를 타고 있다.
- api 컨테이너가 하나라 재배포할 때 LB에서 40초쯤 503 창이 생긴다. CI가 아직 테스트를 안 돌린다.
